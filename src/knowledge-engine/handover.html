We.Publish · knowledge infrastructure · handover

Aldus & the knowledge engine

handover · Tom Vaillant → We.Publish team · june 2026

One knowledge base (RAGFlow, headless on onyx01) holds everything We.Publish knows, every entry tagged on ingest. One librarian — Aldus — (the Hermes runtime on hermes01) is the only thing people talk to, in Slack. This document is the operating handover: what's built, how it's wired, and what closes the vision.

Live today: Aldus answers staff in Slack from a populated KB, with a strict answer contract (every reply carries its sources, confidence, and provenance). The architecture map below is interactive — drag to pan, ctrl-scroll to zoom.

01

The system, end to end

Staff and their coding agents sit on top. The knowledge base is one tagged collection; the namespace tag (public / internal / newsroom:{slug}) is the access scope. Aldus reaches it only through two hardened skills; live CMS state and live code come from their own MCPs, never indexed.

02

Skills Aldus runs

Every read and write goes through a deterministic script, never raw API calls. The skills enforce the rules in code — dataset allowlists, required tags, fail-closed — so a prompt-injection or a model slip can't widen access. Two skills live in Aldus's profile; two CLI tools support ingestion and ops from the box.

kb-retrieve

live
skills/kb-retrieve/query.py

The scoped read path. Aldus phrases a search question; the script runs hybrid search against RAGFlow with the queryable namespaces pinned, and fails closed. Aldus grounds every answer in what comes back — retrieve before answering from memory.

kb-ingest

live
skills/kb-ingest/push_chunk.py

The hardened write path. Validates the full tag schema, refuses any dataset outside its allowlist, and gates promotion: confidence=confirmed requires an explicit --reviewed-by human. In newsroom contexts it force-tags newsroom-asserted.

kb-bulk

tool
knowledge-engine/tools/kb-bulk

Batch ingestion used to populate the KB — corpus-scale loads (GitBook, API references, newsroom profiles) with pagination and tagging. Run by IT from the box, not by Aldus.

wp-kb

tool
knowledge-engine/tools/wp-kb

The ops CLI: health, datasets, query, ingest. How an operator inspects or queries the engine over SSH without touching the RAGFlow UI.

03

Knowledge base — schema & sources

The schema is the catalogue. Every chunk carries these tags on ingest; structure comes from tagging, not folders. The namespace tag doubles as the access scope.

TagValuesRule
namespace reqpublic · internal · newsroom:{slug}The dataset = the access scope. Skills refuse anything off the allowlist.
type reqdoc · support_pattern · decision · setup_summary · architecture · issue_summary · api_reference · implementation_profile · media_profileWhat kind of knowledge this is.
source reqURL · system name · newsroom-assertedNo source, no ingest.
confidence reqconfirmed · likely · unverifiedconfirmed requires --reviewed-by (a named human).
owner reqteam or personWho's responsible for the entry.
newsroomslugOnly on newsroom-related chunks.
repo_path · commitpath + short SHARequired for code-derived knowledge (api_reference, implementation_profile).
last_updated—Stamped automatically.

Isolation, enforced in layers: nobody logs into the engine — Aldus holds the only credentials · the skills refuse any dataset outside their allowlist in code, not in the prompt · newsroom-asserted knowledge is never presented as We.Publish-verified · payments, credentials and member data never enter the index — live CMS state is fetched, not stored.
04

Access points — and what completes the vision

Aldus reaches the world through narrow, purpose-built surfaces. Three are live or built; two more close the loop — one for developer support, one for newsroom support.

Slack

live

The front door. One app, channels-only (no DMs). #dev-aldus and #support-aldus are pinned and live; one private channel per newsroom is added the same way. Home channel set for cron/monitoring delivery.

wepublish-mcp

live

Developer context — live code and docs at HEAD from GitHub/GitBook. Code is never embedded in the KB (embeddings go stale); it's always fetched live through this MCP.

CMS MCP

read validated

Live tenant diagnostics for general support over the We.Publish GraphQL API — curated tools, no arbitrary queries, gated to safe read-only uses. Lets Aldus answer "is this newsroom's setup correct right now?" Read tools validated live against Bajour's production API (api-bajour.wepublish.cloud/v1): site profile, member plans, navigation all resolve, zero schema drift. The permission-gated reads (payment/subscription status) need the scoped token from wepublish#2801. It never writes — sensitive setup data is handled by the secure form below.

GitHub

design ready

Issues now, PRs next. A fine-grained PAT (selected repos, Issues: rw) lets Aldus turn support requests into well-formed issues. PR creation adds Contents/PRs: rw — with branch protection (require a review; bot is no reviewer) as the hard "can't merge" guarantee, since GitHub has no open-PR-but-not-merge permission.

Two additions complete the picture:

Jira — Share Board

suggested · dev support

To complete developer support: wire Aldus to the We.Publish Jira Share Board, where member feature requests and ideas live. Then Aldus can answer "is this on the roadmap / has someone asked for this?", surface related tickets during triage, and file new ones — closing the loop between a newsroom's need and the network's shared backlog.

  • Read: search tickets to dedupe + answer "is this known/planned?"
  • Write (gated): draft a Share Board entry from a support thread, shown before filing
  • Swappable adapter — GitHub Issues remains the phase-1 tracker until this lands

Secure setup form

suggested · newsroom support

To complete newsroom onboarding: a single secure web page where a newsroom enters its payment and setup details — and the page writes them correctly and directly into their CMS database. Sensitive structured data (payment-provider keys, member plans) belongs in a purpose-built, validated form, not in an LLM-composed write — so this stays a deterministic, auditable path, separate from Aldus.

  • Handles secrets securely — payment credentials never pass through the agent or the KB
  • Validates + maps fields to the right CMS mutations; correct-by-construction
  • Aldus assists around it (CMS MCP reads check the result), but never performs the write
05

Operating the box

Everything is on two Hetzner VPS, key-based SSH. Config + secrets live in /root/.hermes/profiles/internal/ (chmod 600, never in git). 

ssh root@hermes01.wepublish.cloud            # the gateway box (Aldus)

hermes -p internal chat                       # talk to Aldus in the terminal
systemctl status hermes-gateway-internal      # Slack gateway (systemd, boot-enabled)
journalctl -u hermes-gateway-internal -f      # live logs
systemctl restart hermes-gateway-internal     # after any .env / config change

# profile dir holds:  .env (secrets) · config.yaml (model, Slack) · SOUL.md (Aldus) · skills/
hermes -p internal config set model.default <model>   # change LLM

# knowledge engine on onyx01, reached via the ragflow-tunnel.service SSH tunnel:
knowledge-engine/tools/wp-kb datasets         # inspect the KB
Hard boundaries (do not relax): KB writes only through kb-ingest; confirmed needs a human reviewer · newsrooms never get RAGFlow access in any form · no CMS writes without dry-run + approval + audit · agents never merge PRs · secrets stay in chmod 600 .env on the server.
