We.Publish · knowledge infrastructure

One knowledge base,
one librarian: Aldus

architecture map · june 2026

One headless knowledge engine holds everything We.Publish knows — public docs, internal support patterns and decisions, and each newsroom's own knowledge, in isolated datasets. One librarian agent — Aldus — is the only thing people talk to: newsrooms in their dedicated Slack channel, staff and developers in theirs.

Nobody logs into the engine. Every read and write goes through skills that enforce dataset scoping in code, every answer carries its sources and confidence, and everything a newsroom tells us stays marked as theirs until a human reviews it.

01

The system

RAGFlow runs headless on onyx01 with three dataset families; Aldus (Hermes runtime) runs on hermes01 as a single Slack gateway serving every channel. Aldus reaches the engine only through two hardened skills over a restricted SSH tunnel; live CMS state and live code are fetched from their own MCPs, never indexed. Isolation, enforced in layers: nobody logs into the engine — Aldus holds the only credentials · the skills refuse any dataset outside their allowlist, in code, not in the prompt · newsroom channels are scoped to public + their own dataset only · everything a newsroom tells us is tagged newsroom-asserted / unverified until a named human reviews it · payments, credentials and member data never enter the index — live CMS state is fetched, not stored · isolation probes must pass before any newsroom channel goes live.
02

The knowledge loop

Every support exchange makes the collection better. Questions are answered from the narrowest valid scope with sources and confidence; what can't be answered becomes a GitHub Issue; what gets resolved comes back as a support pattern — so the same question is never escalated twice.
